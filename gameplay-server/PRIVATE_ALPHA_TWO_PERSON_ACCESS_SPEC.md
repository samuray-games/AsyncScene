## 1. Recommendation

**Owner decision recorded:** Option A is accepted for the first closed pilot: use two separately minted, battle-and-side-scoped bearer capabilities, one for A and one for B. No passkey or person-account service is required for this pilot. Invite and delivery remain owner-mediated and are not implemented by this decision. Before sending B's capability, the owner confirms the recipient using a second known channel (for example, a short live voice/video check against the message account). The invite is one-to-one and manually issued; there is no public signup, discoverable lobby, or general account system.

Treat possession of the bearer as authority to act for that side. A delivery-channel identity check reduces misdelivery and casual impersonation; it does **not** cryptographically distinguish Керил from someone who later steals his bearer. The current Worker cannot make that distinction. The owner explicitly accepts that an active stolen bearer is indistinguishable from its intended holder until revoked. Option B remains an unselected alternative only if the owner later reopens this choice.

Use only the participant's own capability on their device; never place it in a URL, telemetry, logs, screenshots, shared clipboard, or the other participant's browser. The owner-approved default is page memory only. Separate explicit consent on each device permits retaining only that participant's bearer in that origin's IndexedDB. A lost device or suspected disclosure requires operator action from a known generation; otherwise recovery is BLOCKED / STOP. A new device receives a fresh capability only after owner re-verification and a valid replacement procedure. This is not cross-device account recovery.

Use only a dedicated HTTPS gameplay Worker and dedicated gameplay D1 if a later, separately authorized staging step is approved. The remote gameplay client must call that Worker; it must not host privileged operations. The telemetry D1 is never a gameplay transport or store.

## 2. Invite, join, and reconnect flow

### 2.1 One-time owner invitation

1. The owner records A and B as the only two intended people in an owner-controlled roster outside the repository. The roster and contact details are not stored in GitHub, Notion, Worker state, or analytics. This is a proposed human procedure; current code does not enforce a roster.
2. The owner contacts B through a known end-to-end encrypted channel and confirms the same person using a second previously known channel. The invitation identifies the game and asks B to accept. No invite URL containing a bearer token is sent.
3. After acceptance, the owner creates one battle through the trusted operator path: `POST /v1/admin/battles`. A is side A and B is side B. Use a fresh high-entropy `Idempotency-Key` for that creation intent and persist it before the request. If the create response is ambiguous, recover that same intent using the same key and identical participant payload; do not mint a second battle blindly.
4. The server returns the battle ID and distinct A/B capabilities only to the trusted operator. A matching retry using the same idempotency key can recover and re-disclose that original result, so the key and response remain sensitive. The operator must send only A's token to A and only B's token to B, through the verified private channel. Do not paste both tokens into either browser or a shared chat. The operator must not use browser JavaScript or the public client to call the admin endpoint.
5. Each participant opens the same approved HTTPS game origin on their own device, enters the battle ID, and supplies only their own capability through the client. The browser calls `GET /v1/battles/{battleId}` and `POST /v1/battles/{battleId}/commit` with that capability in the Authorization bearer header. The server derives side and participant identity from the active capability; client-supplied side, actor, role, version, or server time cannot choose another identity.
6. There are exactly two participant records in the battle. A third person cannot join through this contract. Replacing B means owner action against B's existing capability record, not a third parallel participant.

Current source does not implement this onboarding UX or deliver the invite. The browser harness in PR #449 is loopback-only and cannot connect two remote devices.

### 2.2 Device persistence and recovery

- **Approved default:** hold the participant's bearer in page memory only. Do not persist it across Safari launches, reloads, or tab closure unless that participant explicitly opts in on that device. After reload without consent, the participant re-enters their own token.
- **Approved per-device opt-in:** ask the participant separately on each device whether to “Запомнить на этом устройстве” (or equivalent clear wording). After affirmative consent only, store that participant's bearer in one origin-scoped IndexedDB record. Declining leaves page-memory-only play available. Do not sync the record across devices.
- IndexedDB remains readable to same-origin script and may be exposed by device compromise, shared-device access, browser backup/sync, or device-unlock access. This accepted bearer risk is part of Option A; HTTPS and CSP reduce some exposure paths but do not make storage theft-proof.
- After network loss, reconnect using the in-memory token for the current page or the opt-in stored token. Retry the same ambiguous commit with the same command identity/receipt path; do not create another battle or a new command identity for the same intent.
- “Забыть это устройство” clears the app-held participant-token reference from page state and deletes that participant's IndexedDB record. This is local deletion only and does not revoke server access; secure zeroization of JavaScript memory is not guaranteed. Admin and recovery keys must never enter page memory, IndexedDB, localStorage, cookies, URLs, or other client storage.
- Moving to a replacement device is not silent token export. The owner re-verifies the participant through the still-open contact procedure; an operator uses the replace flow only from a known current generation, then privately delivers the new capability. If generation is unknown or the replace response may have succeeded but was lost, recovery remains BLOCKED / STOP until verified readback exists (section 5).
- If a device is lost, report it through the owner-approved contact channel. Local deletion cannot be assumed. Revoke or replace only from a known current generation; if it is unknown, BLOCKED / STOP. A bearer alone cannot safely recover itself after loss.

## 4. Trust boundaries and threat model

### Protected assets

- Battle state, unrevealed selections, participant-authored values, command receipts and event/outbox records.
- A and B's individual bearer capabilities, their digests, the encrypted create-recovery result, and recovery-key versions.
- `ADMIN_CONTROL_TOKEN`, which can create battles and revoke/replace participant capabilities.

### Boundaries and controls

1. **Participant browser -> gameplay Worker:** untrusted device and network. HTTPS protects transport in transit. The participant bearer is sent in an Authorization header, never query parameters. Worker maps token digest to a single battle, side, participant ID, active status, and generation.
2. **A browser vs B browser:** separate capabilities. A is not allowed to choose B's side by request input. Side/participant mismatch and stale generation must fail closed. A participant reads only the public view authorized for that participant.
3. **Operator -> admin API:** high-privilege server-to-server boundary. Keep `ADMIN_CONTROL_TOKEN` only in a protected operator secret store/server binding. Admin requests must be issued by a trusted operator process, not browser UI. CORS is not authentication and must not be treated as the security boundary.
4. **Worker -> gameplay D1:** private persistence boundary. D1 stores capability SHA-256 digests, not plaintext bearer values; creation recovery stores an AES-GCM encrypted result. Recovery keys remain server-side, versioned, and separately backed up under PA-05.
5. **Gameplay service vs telemetry:** separate resources and credentials. No battle state, bearer, player text, admin credential, invite roster, or gameplay recovery data may be sent to or stored in telemetry D1.
6. **Owner/operator human verification and delivery channel:** out-of-band trust dependency. A compromised or misidentified channel can deliver B's token to an attacker. The second-channel identity check reduces but cannot eliminate that risk.

### Explicit residual threats

A stolen capability, compromised participant device/origin, malicious same-origin script, operator account compromise, leaked admin/recovery secret, and an authorized operator intentionally misassigning B are not prevented by the bearer design. The Worker has no stable human identity registry or cryptographic binding to Керил. Browser IP, user-agent, CORS, display names, and a secret invite URL cannot repair this gap. Revoke/replace limits future use but cannot retract data already read or cancel a response already in flight.

**Hidden-move invariant:** each commit is accepted for only the caller's capability-derived side. The public result is not revealed until both commits have been accepted and the lifecycle transitions to the committed/revealed phase. Tests must prove A's first commit, B's first commit, retries, and concurrent first commits do not expose the opponent's uncommitted choice.

**Admin-key invariant:** `ADMIN_CONTROL_TOKEN` exists only in server/operator secret bindings. The browser never creates a battle, reads the admin secret, or calls an admin route. The operator tool sends server-to-server requests. Never add the key to HTML/JS, localStorage/IndexedDB, URLs, client-visible environment, GitHub, Notion, screenshots, or telemetry.

### Lost replace response: mandatory BLOCKED / STOP

The integrated Worker source has generation-guarded `revoke` and `replace` operations and implements `GET /v1/admin/battles/{battleId}/capabilities/{side}/status`. The route requires a separate server-only `OPERATOR_READ_TOKEN`, rejects browser `Origin`, `OPTIONS`, and non-GET requests, and returns only the requested side's `generation` and `status`; it does not return tokens or digests and does not write D1. Local Worker/D1 tests passed for this source. The server API has not been deployed, and no real operator identity, credential custody, or recovery runbook has been approved. This endpoint is not evidence of hosted availability or permission to use privileged SQL.

If the `replace` response may have been lost after a successful server-side write, the integrated source now provides an operator-only status route, but this route has not been deployed or verified against the actual hosted service. For any hosted instance without a successful verified readback, the operator cannot know whether the old bearer is still active or which generation is current. Mark the recovery **BLOCKED / STOP**. Do not retry blindly, guess a generation, let either participant inspect operator state, or disclose an admin/readback credential to a browser. Stop issuing access and do not claim recovery until hosted readback is verified and an approved operator procedure is in force:

1. **Operator readback endpoint (implemented in source; hosted gate remains open):** `GET /v1/admin/battles/{battleId}/capabilities/{side}/status` uses a distinct server-only `OPERATOR_READ_TOKEN` and returns only that side's current generation and status. Local Worker/D1 tests passed. The endpoint has not been deployed or verified against a hosted Worker/D1. Before relying on it, the owner must approve the operator identity, read-token custody and actual recovery procedure, then separately authorize deployment and verify hosted readback. This spec does not authorize deployment.
2. **Formally approved emergency D1 read-only procedure (separate operational option):** only after the owner approves it under PA-03/07/08 and G3/G4, verify a genuinely read-only access method/credential, exact account and gameplay D1 identity, fixed SELECT-only query, operator identity, audit trail, and recovery runbook. Do not use an unreviewed `wrangler d1 execute`, broad write-capable credentials, guessed resource identifiers, or an improvised SQL workaround. This procedure is not currently approved or verified.

After a hosted readback is independently verified and used under an approved operator procedure, the operator may deliberately replace from the observed generation (thereby invalidating any unknown bearer) or revoke, then securely deliver any new token after re-verifying the participant. Until then, no retry and no recovery claim; unknown hosted generation remains **BLOCKED / STOP**.

## 8. Proposed token persistence and remote-origin/CSP policy

The token-storage bullets below record the approved storage contract. The origin/CSP bullets are a recommendation only, pending owner selection; nothing here authorizes implementation or deployment.

### Token persistence

- **Approved default:** keep the participant bearer only in page memory. Do not write it to localStorage, cookies, Cache Storage, URL, service-worker state, or IndexedDB without the explicit opt-in below. Reloading, closing the tab, or ending Safari clears the in-page copy; after reload without opt-in, the participant re-enters their own token from the private handoff channel.
- **Approved opt-in contract:** on each participant/device, ask separately for “Запомнить на этом устройстве” (or equivalent explicit copy) before saving. Only after affirmative consent, store that participant's bearer in one origin-scoped IndexedDB record. Do not sync it or store the other participant's token. Declining leaves page-memory-only play available. “Забыть это устройство” clears the app-held token reference from page state and deletes that participant's IndexedDB record. This does not server-revoke the bearer; JavaScript memory clearing is best-effort, not guaranteed secure zeroization.
- **Accepted limitation:** IndexedDB is readable by same-origin script and may be exposed by device compromise, shared-device use, browser backup/sync or device-unlock access. The owner accepts this risk for the pilot. HTTPS and CSP reduce some risks but do not make browser storage theft-proof.
- **Removal and revocation are distinct:** “Forget this device” deletes the local copy only; it does not revoke the server capability. To revoke server access, the owner/operator uses the existing non-browser revoke route with a known current generation. Never put an admin secret or operator control in the browser to make a local delete look like server revocation.
- **Lost device:** tell the named operator through the owner-approved contact channel. If the operator knows the current generation from a successful prior response, use the existing revoke or replace operation; re-verify the participant before sending any replacement token. If generation is unknown, or a replace response may have succeeded but was lost, mark **BLOCKED / STOP** until one of the independently reviewed readback options in section 5 is available. Do not retry blindly. Local token deletion cannot be assumed when a device is lost.

### HTTPS origin and CSP proposal

- **Isolation warning:** the existing game is served at `https://samuray-games.github.io/AsyncScene/`, whose browser origin is `https://samuray-games.github.io`. IndexedDB is scoped to the origin, not the `/AsyncScene/` path. Other pages under this GitHub Pages origin share that storage boundary; another path does not isolate the participant bearer. Do not use this shared origin for the opt-in private client's persistent token.
- **Recommended isolated topology (not an approved hostname):** serve only the private Chat03 staging client at one dedicated HTTPS origin `https://<owner-controlled-private-client-host>` that is distinct from `https://samuray-games.github.io` and is not shared with other apps, paths, tenants or untrusted scripts. Put the gameplay API at a second dedicated HTTPS origin `https://<dedicated-gameplay-worker-host>`. These placeholders are labels for owner-selected hosts, not existing hostnames; create or deploy neither as part of this contract. The gameplay D1 is dedicated and separate from telemetry, subject to separate authorization.
- Future page CSP should preserve current script/style/security directives and set participant `connect-src` to only `https://<dedicated-gameplay-worker-host>` (no `*`, no broad `https:`, no `'self'` unless a separately justified same-origin API is required). Keep the local harness CSP `connect-src http://127.0.0.1:8787` unchanged. Configure Worker `ALLOWED_ORIGIN` to exactly `https://<owner-controlled-private-client-host>` including scheme and host, with no path or trailing slash; reject missing, malformed, wildcard, non-HTTPS or mismatching browser-origin config before serving participant traffic. The existing exact-origin check and narrow participant CORS methods/headers remain; admin routes reject `Origin` and stay server-to-server.
- No current CSP, HTML, Worker, CORS, or deployment setting is changed. The topology above is one isolated scheme for owner decision; exact hosts and CSP deployment approval remain OPEN. Do not infer a hostname or use the GitHub Pages path as an isolation boundary.
